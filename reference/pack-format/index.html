Packs and bundles

A pack is the smallest installable capability: one source family, a set of live tools, or one automation. A bundle is a named selection of packs plus a chat preset and an eval set. The design is ADR 0002 §3; this page is the reference for the files.

The published JSON schemas are pack.schema.json and bundle.schema.json. Both refuse unknown keys.

Layout

bundles/
  packs/<pack>/pack.yaml
  <bundle>/bundle.yaml

Every path inside a manifest is relative to the directory holding it and may not leave that directory (.., absolute paths and ~ are refused).

pack.yaml

Key Required Meaning
name yes Equals the directory name. Lowercase words joined by -.
kind yes context (sources), tool (live tools) or automation.
version yes MAJOR.MINOR.PATCH.
description yes One sentence.
needs_credentials yes true when the pack cannot publish without a credential.
requires.modules okg ontology modules the pack needs.
requires.packs Other packs it needs.
sources context packs Directory of templates, one <source>.yaml per source. Its single top-level key is <source>. A context pack with no sources must declare schemas (records reach it through okg admission, as in ops-record).
schemas Directory of LinkML schema slices.
init_questions File holding an init_questions: list, in okg's profile question format.
invariants File holding an invariants: list. The pack owns them.
freshness context packs with sources {<pack>.<source>: {max_staleness: 24h}}, one entry for every source. A positive integer and one unit of s m h d w (no ISO-8601). archi doctor compares each source's age to it.
link_coverage List of link-coverage targets, see Context quality.
playbooks Directory of playbooks.
skill_triggers File with version: and an intents: mapping.
search_subtypes Subtypes added to the content search profile.
search_profiles Named okg search profiles, {<name>: {description, subtypes}}, added to the instance's search.profiles. Not content.
live_tools archi.tools.* entries for the MCP server.
action_classes File holding an action_classes: mapping keyed by id. Automation packs declare theirs here; a pack that ships the live tools those classes use may declare them too (slurm does), so every instance that installs the pack gets the same payload schemas.
automation automation packs The automation: trigger, context gate, playbook, action classes, proposal schema, budget, levels. See Automation packs.
files Files installed at the same path in the deployment root (okg's files: allow-list applies).
prompt_fragment Markdown appended to the chat system prompt.
prepare Steps run before the pack's first ingest, see Preparing a pack's input.
credentials Environment-variable names the pack reads.

Source templates may reference three kinds of answers: the base questions every instance has (deployment_name, postgres_dsn, archi_data_root, chat_site_name, chat_model; see base/questions.yaml), the pack's own questions, by their local id (${site_url}), and the questions of a pack listed in requires.packs, by their rendered id (${git_code_repo_name} for git-code's repo_name). The last kind is checked when the packs are composed: a reference no selected pack asks stops the render.

Preparing a pack's input

Some sources read a cache that nothing else writes (docsite reads a records cache). A pack declares the step that writes it, so a bare install has its input and no operator runs a downloader by hand:

prepare:
  - name: records-cache                      # unique within the pack
    module: archi.downloaders.static_docs    # run as `python -m <module>`
    args: [--skip-gitlab, --docsite-output, "${archi_data_root}/docsite/records.json",
           --urls, "${urls}"]
    timeout: 300                             # seconds, 1 to 3600; default 600
  • ${id} in an argument is the answer to the pack's own init question id (or to a base question such as archi_data_root), including its default. validate refuses a reference to anything else.
  • A step is python -m <module> <args> in archi's own Python, with no shell and ARCHI_DATA_ROOT set to the instance's data root. module must be a dotted Python name, so a pack can name only code that is installed. A prepare step runs a Python module of the pack's choosing, at archi init or archi add time, with your full environment and your privileges. That is the same trust as installing the pack, but it is used earlier: before okg reads anything. Install packs only from sources you trust, and read a third-party pack's prepare before you init or add it.
  • archi init runs every selected pack's steps, in resolution order, after rendering and before it starts the graph database or reads any source. archi add runs the new pack's steps before it edits the deployment. Neither runs them with --no-okg.
  • A step that exits non-zero, cannot start or passes its timeout stops the command with the pack and step named and the end of its output. Nothing is skipped and no empty result stands in for the missing input. After a failed archi init, remove the half-made instance directory and run it again; a failed archi add leaves the deployment as it was.
  • A step should be safe to repeat. The static-docs downloader merges pages by URL, so a second run only updates them.
  • Steps run once, at install. They are not a refresh: to refresh a cache, run the same module again (for docsite, python -m archi.downloaders.static_docs), or schedule it.

bundle.yaml

Key Required Meaning
name yes Equals the directory name.
version yes MAJOR.MINOR.PATCH.
description yes One sentence.
packs.default yes Packs installed unless removed with --without.
packs.optional Packs offered for --with.
packs.companions {<pack>: [<companion>, ...]}: when <pack> is selected (by default or with --with), each companion comes on too, with the packs it requires. Opt out with --without <companion>. Merged over extends.
extends Bundles whose default packs this one inherits.
chat site_name, default_model, description, suggestions.
answers Install-question defaults, {<rendered question id>: value} (for example analysis_notes_min_notes: 2500). A later bundle overrides an earlier one; an id no selected pack asks is refused.
automations {<automation pack>: {max_level}}: an upper bound on that automation's level. See Levels.
eval Eval set (JSONL).
okg yes Supported AKMON range, PEP 440 (">=0.6.0,<0.7").

Checking manifests

archi bundles validate                 # every pack and bundle archi ships
archi bundles validate path/to/pack    # one pack or bundle directory

Besides the schema, validate refuses:

  • a path the manifest names that does not exist;
  • a credential written as a value: a credentials entry that is not an environment-variable name, a credential-named key in a source template holding a literal instead of ${VAR}, or a credential question with a default;
  • a template reference to a question that neither the base nor the pack declares, unless it names a required pack's question (${<pack>_<id>}, checked when the packs are composed);
  • a prepare step whose module is not a dotted Python name, that repeats another step's name, or whose args reference an unknown question;
  • a freshness key that is not one of the pack's own sources, a value that is not a duration, or a context pack source with no freshness entry;
  • a link_coverage target whose edge (from -[edge]-> to, or the reverse for direction: in) no source of the pack declares in its output_signature;
  • an automation pack that breaks the rules in Automation packs, including any level above L2;
  • a bundle that names an unknown pack or bundle, extends itself in a cycle, or has no credential-free default context pack with sources (taking inherited defaults into account), because a bundle with nothing configured must publish.

It prints every problem it finds and exits 1 if there is any.

Composing an instance

archi render --bundle cern-team --with indico,git-code --instance ~/myteam

render selects packs by ADR 0002 §3.3:

packs = closure(requires, ∪ default(extends*(A, B, ...))) ∪ with − without

in a fixed resolution order: each --bundle in the order given, preceded by the bundles it extends (parents first); their default packs, each preceded by the packs it requires; then --with packs; then --without removals. requires is closed over the defaults only, so a --with pack whose requirement is not selected stops the render with the --with that fixes it, and so does a --without that removes a pack another selected pack needs.

It then merges the packs and writes one okg profile to <instance>/profiles/<name>/ (<name> defaults to the bundle names joined by -). okg looks in ./profiles/, so running okg from the instance directory finds it with no OKG_PROFILES_DIR.

Part Rule Conflict
modules union —
schemas union by relative path same path, different bytes: stops, printing both digests
sources id <pack>.<source>; file source-defaults/<pack>.<source>.yaml —
init questions base questions, then each pack's as <pack>_<id> (flag --<pack>-<id>) same id, different definition: stops
invariants union; each stays with its pack same name, different body: stops
freshness union; each stays with its pack —
link coverage each target becomes an invariant <pack>_link_<name>, owned by its pack same invariant name, different body: stops
search content subtypes union —
other search profiles union by name same name, different body: stops
playbooks, skill triggers union by file name / intent id different content: stops
action classes union by id different body: stops
files union by path different bytes: stops
chat prompt the base prompt, then each prompt_fragment in resolution order a pack shipping chat-system-prompt.md or skill-triggers.yaml as a playbook: stops
chat scalars from the last --bundle given (a child before its parents); other values are printed as notes —
chat suggestions union —
okg range intersection empty: stops

A pack that is not selected contributes nothing: rendering a selection with --with P --without P gives the same bytes as rendering it without P. The profile directory is rebuilt from scratch on every render.

The base questions, deployment defaults and chat prompt every profile starts from are in python/archi/bundles/base/.

Packaging and discovery

The archi-kb wheel carries bundles/ and skills/ as real files under archi/_payload/ (symlinks in the repository are followed at build time). archi bundles list and archi bundles show NAME find packs and bundles through two entry-point groups, so another package can add its own:

[project.entry-points."archi.packs"]
mywg = "mywg_packs:packs_dir"      # returns a directory of <pack>/pack.yaml
[project.entry-points."archi.bundles"]
mywg = "mywg_packs:bundles_dir"    # returns a directory of <bundle>/bundle.yaml

The value is a callable returning the directory, or the directory itself; the name labels the provider in archi bundles list. Two providers shipping a pack or bundle of the same name, or an entry point that fails to load, are listed as problems and do not hide the rest. What an external package must declare, and how to test it, is in Contributing a pack.

A bundle directory that holds an okg profile.yaml and no bundle.yaml is listed as a legacy profile, and archi render --bundle <name> --instance DIR copies it, symlinks followed, to DIR/profiles/<name>/. Every bundle archi ships is now a bundle.yaml (cern-team since PACT r3-packs-split). Either way the profile lands in <instance>/profiles/, and okg run from the instance directory finds it, so no step sets OKG_PROFILES_DIR.

archi.lock, archi add, archi diff

archi render also writes <instance>/archi.lock. Commit it with the instance. It records the selection (bundles, --with, --without), the okg range and the okg version it was rendered with, each bundle's and pack's version, provider and content digest, a sha256 of every rendered profile file, and what the renderer composed that okg does not read: freshness SLOs, live tools, action classes, and the pack that owns each source. archi render --deployment DIR also records the installed okg deployment.

archi add indico --deployment deployments/myteam --answer indico_base_url=https://indico.cern.ch
archi diff            # exit 0: no drift; 1: drift; 2: no usable lock

archi add <pack> re-renders the instance with one more pack (and whatever it requires that the instance lacks), then adds to the installed deployment only what is new: the pack's registry entries with this deployment's answers filled in, schema slices, files, playbooks, invariants, skill triggers, modules and search subtypes. A file the deployment already holds with different content stops the add; archi does not overwrite what the instance changed. If the deployment is in a git repository the change is committed. Then archi runs the okg steps the quickstart used to list as manual ones:

okg catalog ownership claim --deployment DIR --json
okg catalog load --deployment DIR --apply --json
okg ingest --deployment NAME --include <the new source ids>
okg run --once --deployment NAME --apply

--no-okg stops after the edit and the commit. New questions are answered with --answer <rendered id>=<value>; any not answered take their defaults.

archi diff reports three kinds of drift: rendered profile files edited, added or missing since the render; packs and bundles whose installed version or content no longer matches the lock; and, for the recorded deployment, registry entries that differ from what the rendered profile produces with the deployment's own install answers (an entry edited by hand, removed, or added outside archi).

Context quality

ADR 0002 section 6.1 asks that the context layer be measured, not assumed. Packs carry three of the measures; the fourth, the context eval, is a question set run by archi eval --context (see archi eval).

Freshness. Every source of a context pack declares max_staleness in freshness:. No source template sets a schedule (their triggers are manual and reconcile), so each value is a judgment: how old the source may get before an answer from it is likely wrong, written in a comment above the freshness: block. archi render copies the values into archi.lock (composed.freshness).

archi doctor has a source-freshness check. It runs okg doctor --check sources --deployment <name> --json and reads each source's coverage.watermark.last_reconcile_at, the time of its last completed reconcile in okg's source_watermarks. A source is late when that age passes its max_staleness, and also when okg lists no run for it. archi doctor --json lists every source in the check's data.sources:

{"source": "monit-live.monit_sam", "age": "40h", "max_staleness": "36h", "ok": false,
 "age_seconds": 144000, "max_staleness_seconds": 129600,
 "last_reconcile_at": "2026-10-23T20:00:00+00:00", "reason": "last run 40h ago, over the 36h limit"}

The check is skipped, and says so, for an instance with no archi.lock.

Link coverage. A pack that carries identifiers other sources refer to (sites, datasets, runs, releases, tickets) declares how well they must link:

link_coverage:
  - name: storage_endpoint_site   # invariant: cms_catalogs_link_storage_endpoint_site
    from: storage_endpoint        # nodes that carry the identifier
    edge: contains
    to: site
    direction: in                 # `in`: site -[contains]-> storage_endpoint; default `out`
    min_fraction: 0.9             # share of `from` nodes that need such an edge
    severity: warn                # default; `error` blocks the publish

Composition turns each target into an okg invariant in the invariants.yaml format. It returns one row, with the counts, when the share of linked nodes falls short, and no row when the subtype is empty (the pack's coverage invariant reports that). Targets are warn so that thin data cannot block a publish; set error where a miss should. Declare a target only for an edge the pack already emits.

Context gate. archi.ops.context_gate evaluates a gate (sources, maximum staleness, minimum context-eval score, required invariants) against the current generation's facts and returns pass, or fail with each failing check named (freshness:<source>, context_eval, invariant:<name>, published). Facts come from archi doctor --json (facts_from_doctor), plus invariant results and the context-eval score from the caller. A missing score or result is a failure. published: true asks only that the graph has a published generation; it is the gate of an automation that reports on the instance's own health, which must keep running while a source is stale.

Automation packs

An automation pack (kind: automation) declares one automation and the typed actions it may propose (ADR 0002 sections 7.2 and 7.3). The pack holds the declaration only. The runtime that runs it is PACT r3-ops-runtime.

One pack declares one automation, in an automation: block of pack.yaml. The action classes live in the pack's action_classes file, which the composer already merges by id across packs; the block lists the ids this automation may propose.

name: ticket-triage
kind: automation
version: 0.1.0
description: Reads new tickets and drafts or proposes a response.
requires: {packs: [redmine]}          # packs whose live tools act as mediators
playbooks: playbooks/
action_classes: action_classes.yaml
needs_credentials: false
automation:
  trigger: {type: ticket_queue, system: redmine, queue: cms-comp-ops}
  context_gate:                       # the keys of archi.ops.context_gate.GateSpec
    sources: [redmine.tickets]
    max_staleness: 24h
    min_context_eval_score: 0.8       # the newest `archi eval --context` run's graph recall@k
    max_age_days: 14                  # optional; that run may be at most this old (default 14)
    invariants: [redmine_link_ticket_site]
  playbook: triage.md                 # under playbooks/
  action_classes: [draft_reply, set_ticket_status]
  proposal_schema:                    # JSON Schema; see below
    type: object
    required: [summary, evidence_ids, action_class, payload, confidence, rollback]
    properties:
      summary: {type: string}
      evidence_ids: {type: array, minItems: 1, items: {type: string}}
      action_class: {type: string}
      payload: {type: object}
      confidence: {type: number, minimum: 0, maximum: 1}
      rollback: {type: string}
  budget: {cost_per_run: 0.5, cost_per_day: 10, runs_per_hour: 20}   # USD
  default_level: L1      # where it starts when the instance sets no level
  max_level: L2          # the most this pack allows

# action_classes.yaml
action_classes:
  set_ticket_status:
    payload_schema: {type: object, required: [ticket_key, status], properties: {...}}
    mediator: archi.tools.redmine:set_status   # a live tool, or a workflow step name
    reversible: true
    blast_radius: One ticket's status field.
    max_level: L2

Choices worth knowing:

  • Trigger. schedule needs cron (five fields). ticket_queue needs system (redmine, jira or servicenow, or a list of them) and queue ("*": every ticket the instance ingests; queues: in ops.yaml narrows it). signal needs source (a rendered source id) and condition (text). A cron that can fire more often than budget.runs_per_hour is refused. The check reads the minute and hour fields (numbers, ranges, lists, * and steps) and counts the busiest hour; the day, month and weekday fields are treated as unrestricted, so it is an upper bound. It does not handle @daily style macros or names (MON, JAN) in the minute or hour field; those are refused.
  • Context gate. The same keys and the same parser as the runtime gate (archi.ops.context_gate.GateSpec). The gate must name at least one check, because a gate that checks nothing cannot make the automation depend on measured context (D12).
  • Optional inputs. narrow_to_selected: true is for an automation that can read several optional packs. The renderer keeps only the gate sources, and the ticket_queue systems, whose pack the instance selected; it writes what it left out under not_selected, and refuses an instance that selected none of them. Without it every gate source must be installed, or the gate fails on every run.
  • Mediator. archi.tools.x:fn must appear in live_tools of this pack or of a pack in requires.packs. Required packs are found through the catalog, so they may come from any pack root: a third-party automation can require a shipped pack. Anything else must be a registered workflow step. Steps live in the registry archi.ops.steps, the one place the runtime registers them, and only steps with no external effect exist: record_finding (highest level L0, writes a finding to the ops record), draft_reply (L1, stores a draft, never sends) and draft_issue (L1, writes issue files in the instance repository and commits them there; see Instance health). A step that has an implementation (draft_issue) runs at L1 with no escalation: the halt check and the at-most-once record of a mediator still apply, and it gets the instance directory in its context. A step without one is recorded on the proposal and never runs. A live tool never runs at L1. An action class whose mediator is a step may not have a max_level above the step's. An action that changes an external system (a ticket update, a restart) must be a live tool of a tool pack; an automation never calls an external system any other way (ADR 0002 section 7.2).
  • Proposal schema. The proposal is the ops_proposal record of ops-record. The schema must be a valid JSON Schema and must require summary, evidence_ids, action_class, payload, confidence and rollback with these types: summary, action_class and rollback strings; evidence_ids an array of strings; payload an object; confidence a number with minimum >= 0 and maximum <= 1. It may not name other properties, and may add constraints such as minItems: 1 on the evidence. The runtime fills the other record fields (incident_id, mode, autonomy level, generation read) and serialises payload to JSON text, because the record stores it as text.
  • Budget. cost_per_run, cost_per_day and runs_per_hour must be greater than zero, and a run may not cost more than a day.
  • Duplicate keys. A key repeated in a manifest (the automation block included) or in the action_classes file is refused. YAML would otherwise keep the last one silently.

Levels

Three places set a level for one automation, and none may name L3:

Where Key Meaning
pack automation.default_level the level it starts at when the instance sets none
pack automation.max_level the most the pack allows; each action class also has a max_level
bundle automations: {<name>: {max_level}} in bundle.yaml an upper bound for the bundle's instances; <name> is the automation pack
instance automations: {<name>: {level}} in archi.yaml the level to run at

The effective level is the lowest of the instance level (the pack default when the instance sets none), the bundle bound and the pack maximum. When two selected bundles bound the same automation, the lower bound counts. archi.ops.levels.effective_level(...) computes it and raises LevelError for L3 or an unknown value in any input, so the runtime can call it at run start. archi bundles validate, loading archi.yaml and effective_level all refuse any value other than L0, L1 or L2, citing ADR 0002 D13. A name under automations: in archi.yaml must be an automation pack the instance selected; archi doctor (check automation-names) and archi.ops.levels.instance_levels(...), which the runtime calls, refuse a misspelled name instead of ignoring it. Without a catalog, validate_pack reports a mediator that needs a required pack's tool as not resolvable; it does not guess from neighbouring directories.

What the renderer writes

For each selected automation pack, archi render writes <instance>/automations/<name>.yaml and records the same declaration in archi.lock under composed.automations. It holds the trigger, context gate, proposal schema, budget, default_level, pack_max_level, bundle_max_level (the lowest bound any selected bundle sets, or null), the playbook as its path in the rendered profile (skills/<playbook>) and the action class ids. The file also carries the action classes in full (action_class_definitions); the lock keeps those once, under composed.action_classes. The instance's own level is not rendered: it is set in archi.yaml. archi add of an automation pack re-renders both.

archi bundles validate also refuses: a missing automation: block (or one on a pack of another kind), a missing playbook file, an action class id that is repeated, listed twice or not defined, an invalid payload_schema, a mediator that resolves to neither a declared live tool nor a registered step, a bundle bound for a pack that is not an automation pack, and a missing or mistyped proposal field.

Running automations (archi ops)

An automation runs as an okg deployment workflow, archi.ops.workflow. Any render that selects an automation pack writes runtime: {enabled: true, workflows: [archi.ops.workflow]} into the deployment defaults, so it is in deployment.yaml when okg install starts. (Editing runtime: after install makes publish refuse until okg catalog load --apply.)

Because the runtime is on from the start, okg install without --no-publish stops at its last stage (the DBOS schema does not exist yet). archi init uses okg install --no-publish and okg provision, which finish on okg 0.2.0 (not yet checked on 0.4.0 with an automation selected), and then runs okg runtime bootstrap; if a later okg stops provision on the missing schema, archi init bootstraps and ingests in-process (okg ingest --inline, okg run --once --apply). archi up repeats the bootstrap, which is idempotent. The stack has no runtime worker yet: start okg runtime worker --deployment <name> yourself, with ARCHI_INSTANCE, OKG_DSN, ARCHI_OPS_DEPLOYMENT and OKG_ROLE_SECRETS_FILE (the instance's .secrets/role-secrets.json, for okg's read-only roles) set.

okg publishes only from a committed instance repository. archi.yaml and ops.yaml are in it, so commit an edit to either before the next publish (archi ops promote commits its own).

Settings that belong to the instance, not the pack:

  • archi.yaml, automations.<name>.level: the level to run at. L3 and unknown values are refused when archi.yaml loads, and again at run start.
  • ops.yaml, automations.<name>: mode (shadow, the default, or live), timeout_seconds (how long an L2 escalation waits; default 4 hours), estimate_cost (checked against the budget before each proposal; default the pack's budget.cost_per_run), promotion (the PACT change archi ops promote opened; see below), and the proposer and outcome. The proposer's kind is stub (fixed answers, until the model-backed proposer lands) or instance-health (see Instance health). test_gate_seconds is for tests only.

An automation whose trigger is schedule gets a signal from the scanner for its latest cron time (tick-<UTC time>, source schedule, entity the instance name; archi.ops.schedule). A scan that runs again in the same cron time adds nothing, and a worker that was down adds one tick, not a backlog. No tick is added while the scanner is halted.

One scanner (archi_ops_scan, a @deployment_scheduled workflow) starts the next run of each automation that has none in flight (one at a time: a run waiting hours for a person holds that automation's next signal), with the workflow id <automation>~<signal id>~<attempt>. Neither an automation name nor a signal id may contain ~, so two runs never share an id. Each external effect is a durable step. A live automation whose context gate fails runs in shadow for that run, with the failing checks in the proposal's mode_reason, and it stays in shadow until a promotion approved after the demotion. The demotion is written to archi_ops.demotions when it happens, so the very next run sees it without waiting for a publish; the published ops records carry the same history.

mode: live in ops.yaml is a request. The runtime counts it only while the PACT change named by promotion: is approved in okg's decision ledger; with no such change, or one still awaiting review, the run is in shadow and its proposal's mode_reason says "not promoted: ...". Hand-editing ops.yaml to say live changes nothing, and so does naming another approved change: the change must carry this automation's name in its own promotion.json, must be the newest promotion change for it, and its approval must come after the latest demotion. If okg cannot be run to read the ledger, the run is in shadow with that reason.

An L2 proposal waits for an okg escalation. Only an approval made before the deadline, by a named person, for that proposal and escalation, reaches the mediator step, which checks halt and the escalation again.

The mediator contract

A mediator is a live tool called as tool(payload=..., context=...); the context carries idempotency_key (the run id), proposal_id, workflow_id and dsn. The runtime calls it at most once per key: it records an attempt in archi_ops.mediations before the call, and a replay that finds an attempt with no recorded end (the worker died mid-call) does not call again. It records the action as unknown and the outcome as unknown, "possible duplicate prevented; check the external system". A tool that can run at L2 must also be listed in its pack's idempotent_tools: (a subset of live_tools:; archi bundles validate refuses an L2 action class whose tool is not): given the same key twice it has the effect once, because the step cannot know whether a crashed call finished.

Runbook: an unknown outcome after a crash may mean the tool ran or did not. The attempt row is written before the call, so a crash between that row and the tool call leaves the same trace as a crash inside the call. Check the external system before acting; do not assume it ran, and do not assume it did not.

Commands

Command What it does
archi ops status [--json] Effective level, mode, scanner state, pending escalations, today's budget against its cap, shadow counts and scores.
archi ops pending Escalations waiting for a person.
archi ops approve <id> [--note] [--as] Approve (reject refuses). Only an open escalation about an ops_proposal: of this instance's automations is accepted; a timed-out or already-decided one exits non-zero with the reason.
archi ops halt [--no-cancel] Pause the scanner, answer each open escalation of a run with reject (decided by archi ops halt), cancel runs that have not finished, record them as halted. It reports any escalation it could not close and exits non-zero. --no-cancel leaves runs in flight; their mediator step refuses to act.
archi ops resume Resume what halt paused. A cancelled run is not resumed; its signal runs again as attempt 2.
archi ops promote <automation> Needs a shadow report that passes promotion_readiness (thresholds: --min-proposals and the others). Opens a PACT change in the instance repo that holds the shadow report and the thresholds used, with the readiness verdict as its junit evidence, names it in ops.yaml (mode: live, promotion: <change>), commits both, and stops. An operator then approves it: okg pact decide <change> --verdict approve --principal <name>, a step archi never takes; commit the archived change. Until then the automation runs in shadow. Refuses without a passing report, and outside a repository. .okg/ is ignored by the instance repo.

decided_by is the OS user. --as X is recorded as " for X", not as X: nothing authenticates the caller until okg offers an authenticated proposal API (docs/ops-runtime-akmon-asks.md, O3). Put --instance, --deployment and --dsn (default $OKG_DSN) before the subcommand: archi ops --dsn ... pending. python/tests/ops/scratch_ops_runtime_run.sh runs every case above on a scratch okg 0.2.0 instance.

Instance health

The instance-health pack (ADR 0002 section 7.5, PACT r3-ops-self-monitoring) is the automation that watches an instance. It is an ordinary automation pack, hourly (7 * * * *), with no model call, and at most L1: L0 records what it finds, L1 drafts the issues. Select it with ops-record, which it writes to:

archi init myteam --bundle cern-team --with ops-record,instance-health

Then switch it on in the instance's ops.yaml (nothing runs for an automation ops.yaml does not name), and start the runtime worker as for any automation:

automations:
  instance-health:
    mode: shadow                  # live only after `archi ops promote instance-health` is approved
    proposer: {kind: instance-health}

Signals. Each run reads, and nothing else:

Signal Read from Problem key
doctor archi doctor --json, every failing check (warnings with include_warnings: true) <check id>/instance; source-freshness/<source> for each late source
ingest okg sync frontier --json: a source whose frontier is blocked (failed run, blocked publish) ingest/<source>
automation errors the ops records, through the reader of archi.ops.shadow: an automation with at least min_decisions decisions in window_hours of which max_rate or more are error, invalid_proposal or refused automation-errors/<automation>
eval every report.json that archi eval wrote under <data root>/eval/ (its default --out; eval.reports_dir reads elsewhere), for the bundles archi.yaml lists (others are left out, and the proposal says so). Per bundle, the latest run is a problem when it ended execution_failed (a failed signal, an error; no score is judged), when it passed fewer questions than the bundle's threshold (an error), or when its score (passed / total) is more than min_drop (default 0.1, one question in ten) below the mean of up to three earlier runs of the same model and question set (a warning). Earlier runs that ended execution_failed, or in which any question did, are left out of that mean; such questions in the latest run are named in the issue as a model or endpoint failure. With no report at all, the signal is skipped, and the proposal says so. When the latest run has no earlier run to compare with (one run so far, or none of the same model and question set), it is judged on its threshold only, and the proposal says the trend was skipped (eval-trend). A newest run older than max_age_days (default 14) is a note in the proposal (eval-stale), not an issue eval/<bundle>

A signal that cannot be read (okg down, archi doctor crashing, a malformed eval report) is itself a problem, monitor/<signal>, and that signal's other issues are left as they are for the run: failing to look is not evidence of health.

Issues. The key is the check plus its subject, never a time or a count, so the same problem is the same issue run after run. A run makes the tracker match what it found:

  • a new key opens an issue; a changed text updates it; an unchanged one writes nothing;
  • a key no longer found, in a signal that was read, marks its issue resolved (never deleted);
  • a resolved key that returns reopens the same issue.

The text of an issue holds no age or run time (a late source shows its last reconcile time and its limit), so a lasting problem does not rewrite its issue every hour.

Trackers. Set proposer.tracker in ops.yaml:

kind Where the issues go Credential Runs as
local (default) .archi/issues/<check>--<subject>.md in the instance repository, committed by the run (a commit limited to that path) none the step draft_issue, at L1
gitlab (url, project, token_env) issues labelled archi-health on that project, through /api/v4 the variable token_env names the live tool archi.tools.instance_health:sync_forge_issues, at L2
github (repo, token_env, optional api_url) the same on a GitHub repository, through /repos/<repo>/issues the variable token_env names the same live tool, at L2

Only the name of the token variable goes in the file; a value is refused. A forge issue is found by a marker comment at the end of its body, not by its title. Why the split: writing files under .archi/issues/ in the instance's own repository has no external effect, so it is a workflow step and runs at L1 without an escalation. A forge is an external system, so ADR 0002 section 7.2 puts it in a live tool, and a live tool runs only after a person approves it (L2). The pack ships with maximum L1, so the forge tracker is available to an instance that raises the pack's max_level to L2 (and its own level in archi.yaml); each sync is then an escalation. A draft pull request for a mechanical fix is not built yet.

ops.yaml can also set ignore_checks: [services], include_warnings, error_rate: {window_hours, min_decisions, max_rate} and eval: {min_drop, reports_dir, max_age_days} under proposer. archi eval keeps each default run in its own <data root>/eval/<bundle>/<UTC stamp>/ (--keep, default 20), so a trend needs no extra flag.

Ticket triage

The ticket-triage pack (ADR 0002 section 7.4, PACT r3-auto-ticket-triage) triages new and updated tickets from the ticket packs the instance selected: tickets (Redmine, and any JIRA through its generic reader), jira and servicenow. It is optional in cluster-manager and cms-comp-ops, starts in shadow at L1, and makes no model call.

archi init mycluster --bundle cluster-manager --with ticket-triage

# ops.yaml
automations:
  ticket-triage:
    mode: shadow
    queues: [Cluster Ops]          # optional: projects (ServiceNow: assignment groups) to triage
    proposer: {kind: ticket-triage}

Signals. The scanner reads each system's tickets at the latest published generation and adds a signal for every open ticket updated since the last one it saw (archi_ops.ticket_cursors). The first read only sets that starting point, so installing the pack does not triage the existing queue.

A run reads, at its pinned generation, the ticket, related tickets (okg's search over the same system), documentation (proposer.doc_subtypes) and ops-record precedents on those tickets, and proposes (archi.triage.proposer):

Level Action class Runs as
L0, L1 draft_reply: category, likely component, related tickets, precedents, documentation and a suggested reply, each claim cited [n] to a node id the step draft_reply; recorded on the proposal, never sent
L2 assign_ticket (an unassigned ticket whose related tickets mostly went to one person or group) or set_ticket_status (to triaged_status, from one of triage_from) the live tools archi.tools.tickets:assign_ticket and :set_ticket_status, after a person approves the escalation

An L2 tool checks the approval again, refuses a stale proposal (the field changed since), writes the field with a note on the ticket that names the approver and the escalation, and reads it back. The API and the names of its credential variables are set per system under proposer.systems (see the pack's skills/triage.md); the tool sends only to the endpoint configured there, and only for a ticket whose link lies under it.
