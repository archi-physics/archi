archi eval

archi eval checks that an instance answers. It asks the questions of a bundle's smoke set through a small agent that reads the instance only over its MCP endpoint, then checks each answer with fixed rules. It needs a model, and the model is a local one, so a run costs nothing.

A bundle that installs green can still answer nothing. The smoke set turns "it works" into a check you can run.

This harness is a stop-gap

The eval framework tracked in #619 replaces it. The question files and the report format are kept so they can move across. The context eval (retrieval scored against a lexical baseline) needs no model and is described below. Its raw-document baseline adds two agent arms that do use a model, under a spend cap.

Run it

archi eval --bundle cern-team --model qwen3:8b

Run it from the instance directory, or pass --instance DIR. The instance must be up (archi up): the agent connects to its MCP endpoint with the bearer token in the instance .env. A model server must answer too. The default is a local Ollama at http://127.0.0.1:11434/v1; --model-url names another. Pick a model that can call tools; the agent has no other way to read the graph.

Option Meaning
--bundle X The bundle whose set to run. Repeat it for several. Default: the instance's bundles that ship a set.
--instance DIR The instance directory (default: the current directory).
--model M The model name at the endpoint. Default: the bundle's chat.default_model, if it sets one.
--model-url URL An OpenAI-compatible base URL. Must be on this host or a private network.
--out DIR Write the report straight into DIR, replacing the one there. Default: a new eval/<bundle>/<UTC stamp>/ per run under the instance's data root, outside the instance repository; latest.json beside the runs names the newest.
--keep N Without --out: keep the newest N runs per bundle and delete older ones (default 20; 0 keeps all). Only directories named like a run stamp are deleted.
--mcp-url URL An MCP endpoint other than the instance's own. The instance is then not read at all: reports go under ./eval-reports/<bundle>/<UTC stamp>/ in the current directory unless --out is given; the bearer token comes from OKG_CHAT_MCP_TOKEN, --bundle is required, and there is no default chat prompt. An instance's token is never sent to another endpoint.
--chat-prompt FILE The chat system prompt to give the agent. Default: the instance's deployments/<name>/skills/chat-system-prompt.md, the one archi up gives the chat.
--max-steps N Tool-call rounds allowed per question (default 8).
--no-think Ask a reasoning model to skip its thinking pass.
--allow-remote-model Allow a model endpoint off this network. This can cost money; it is off by default.

The command prints one line per question, writes report.md and report.json, and exits:

Exit Meaning
0 The set passed at least the bundle's threshold.
1 It passed fewer than the threshold.
2 The run could not execute: the MCP endpoint offered no tools or was unreachable, the model failed on every question, a file was unusable, or the run stopped on an unexpected error. The report is still written; questions answered before the stop keep their result.

What the agent is given

The system message holds three things, in this order: the instructions the MCP server serves in its initialize reply (how to search, filter and read), the bundle's chat system prompt, and a short answer-format note. The first two are what an operator's chat agent sees. The note comes last because it overrides the chat prompt's citation style: the checks read node ids. Its example ids are placeholders that no shipped set expects, so a model that copies them gains nothing. The report records a hash of each part.

What a question checks

Each bundle ships bundles/<bundle>/eval/smoke.yaml: at least ten questions and a pass_threshold, currently 7 of 10 for both sets. The number is a starting value; it will be raised once more than one model has results.

- id: fts3-version
  question: Which FTS version does the FTS3 documentation describe?
  must_cite: {sources: [docsite]}   # ids, any_id, subtypes or sources
  must_contain: ["3.12"]            # also must_contain_any

The agent answers with the node ids it used. A question passes when:

  • the answer names a node that a tool returned in this run (an invented id does not count), and that node meets every must_cite key given: its id is one required, or its subtype or source is one listed; and
  • the answer holds every must_contain string, ignoring case, hyphens between words and extra spaces ("low-level" matches "low level").

There is no LLM judge. A wrong answer that cites the right source and uses the right words passes; the set is a smoke check, not a grade. Results depend on the model, and a small model may miss questions a larger one gets.

A question ends as pass, fail (the answer did not meet the rules, or the model ran out of steps) or execution_failed (the model endpoint errored). If the MCP endpoint has zero tools, the whole run is execution_failed: an agent with nothing to read with cannot be scored.

The report

When a question checks a cited node's subtype or source and no tool result said it (a model that asks filter for only some fields gets rows without them), the runner reads that node once with inspect after the answer, with no model involved, and lists it under lookups in the report with whether the read worked. Only a node a tool returned as a result is read, never an id the model saw only inside another record's text, and only while the question's check is not yet met. Only what that read says about the cited node counts.

report.json records the model, the MCP tools it saw, a hash of the prompt and tool schemas, the threshold, and per question the status, the failure reasons, the cited node ids with their subtype and source, each tool call, tokens in and out, wall time and the answer text. report.md is the same for reading.

The instance-health automation reads every report.json under <data root>/eval/ and raises an issue per bundle when the latest run is execution_failed, below the threshold, or more than min_drop below the earlier runs of the same model and question set. Each default run is kept in its own <data root>/eval/<bundle>/<UTC stamp>/, so two runs are enough for a trend. A run written with --out replaces the report in that directory. It does not read context evals: it skips <data root>/eval/context/ and hidden directories.

The shipped sets

Bundle Corpus the questions rely on
cern-team The bare defaults: the FTS3 and Rucio documentation pages and Indico event 1716863. Run it on an instance made with archi init <name> --bundle cern-team and no changes.
cms-physics An invented fixture corpus: two analysis notes, three TWiki topics, two CDS records and the CMSSW 15_0 release map. python/tests/evaluation/bundle_lab.py installs it into a scratch database. On a real CMS instance, this set checks only that the corpus is there.
cluster-manager An invented cluster: four documentation pages (draining a node, scratch space, GPU jobs, maintenance windows), three Redmine tickets, and the ops records of two incidents. cms-comp-ops has no set.

In CI

The nightly workflow (nightly-e2e) runs archi eval --bundle cern-team after the cited-answer step, with a small model on the CPU runner, and reports the score in the job summary. A CI gate on bundle changes across all four bundles is not built; it waits for the #619 framework, because a gate needs either a slow local model or a paid API model.

Context evals: archi eval --context

The context eval scores retrieval alone: did the search bring back the evidence that answers the question? It asks no model. For each question it calls the instance's MCP search tool directly and checks whether the question's gold node ids, the evidence chosen by hand as the answer, come back in the top k rows.

archi eval --context --questions /path/to/operator-questions.yaml
Option Meaning
--context Run the context eval instead of the smoke set.
--questions FILE The question file. Default: $ARCHI_CONTEXT_EVAL_QUESTIONS, else the bundle's eval/context.yaml. No bundle ships one, so name a file. A path that does not exist exits 2 and names the path.
--k N The recall cut-off. Default: the file's k, else 10.

--instance, --mcp-url and --bundle work as for the smoke set. The model options are used only by the agent arms.

The question file

The format is the smoke format with gold added, so a smoke file whose questions carry gold ids can be used as it is (pass_threshold, must_cite and must_contain are read and ignored):

bundle: cern-team
k: 10                 # optional (default 10)
min_recall: 0.6       # optional: exit 1 when the graph arm's recall@k is below it
questions:
  - id: fts3-what-is
    question: What is FTS3?
    gold: [documentation_page:2275b50c]   # the node ids that answer it

A question without gold is listed in the report and not scored. The bundle name is used in paths, so it may hold only letters, digits, ., _ and -.

Where the question set lives. An instance's operator questions are private. They are never committed to this repository, which is public. Keep the file with the instance (or anywhere outside this repository) and name it when you run:

archi eval --context --questions /path/to/operator-questions.yaml
# or
export ARCHI_CONTEXT_EVAL_QUESTIONS=/path/to/operator-questions.yaml
archi eval --context

--questions wins over the variable. The only question file in this repository is the test fixture, python/tests/evaluation/fixtures/context.yaml, whose ids are invented. On an instance, a set whose bundle the instance does not list is refused (exit 2), so a fixture or another instance's set cannot produce a run the context gate would read.

The two arms

Each question runs twice, in two arms (two ways of searching):

Arm What it calls
graph search with the server's defaults: the search an operator's agent makes. Passages roll up to their records.
baseline search with method: lexical, rank_by: self and expand_concepts: false: the server's lexical index over chunks and attributes, each text unit ranked on its own words, with no roll-up to records and no concept expansion.

The baseline is a lexical baseline, the closest the MCP surface comes to keyword search over the raw documents. It is not a separate index of the raw documents: it searches the same server's lexical index, which covers chunks and node attributes. Chunk rows can fill its k slots where the graph arm returns one row per record, so part of the difference between the arms is that roll-up, not the graph's links. The graph arm is lexical search too (okg's default method), with concept expansion and record roll-up on, so the delta measures those two, not graph links. A question file can replace either arm, or add more, under arms:, for example baseline: {tool: search, arguments: {method: lexical, where: {type: document_chunk}}}. The harness always sets query (the question) and limit (k) itself. A file that replaces the graph arm makes the run informational only: on an instance it is refused (exit 2) unless written elsewhere with --out, and the context gate refuses any report whose graph arm is not the default.

Each call asks okg for JSON (_meta okg/result_format: json, which okg 0.2.0 serves). A server that answers in text instead is read from its row lines, [n] <id> (<subtype>) at the start of a line; an indented line is part of an excerpt and never a row. A row counts as a hit for a gold id when the row's id is that id, or when the row is a passage whose record (parent in JSON, in <id> on a text row line) is that id. Ids in a row's title or excerpt do not count. The generation each call read is taken from the reply.

The report

Each run gets its own directory, so the history is kept: <data root>/eval/context/<bundle>/<UTC stamp>/report.json and report.md (the stamp is YYYYMMDDTHHMMSSZ, with -2, -3, ... added when two runs finish in the same second). A run is written into a hidden .<stamp>.tmp-<pid> directory beside it and renamed into place only when both files are complete, so a crash never leaves a half-written report where a reader looks; readers skip names that start with a dot. With --mcp-url the default is eval-reports/context/<bundle>/<UTC stamp>/; --out DIR writes to that directory instead.

The report holds, per arm, recall@k (the share of each question's gold ids found in the top k, averaged over questions), MRR (the mean of 1 / rank of the first gold hit) and the number of failed calls; the total of failed calls (errors); the baseline delta (graph minus baseline recall@k), computed only over the questions on which both arms executed; the generation the graph arm's calls read; the question file's path, its sha256 and the number of scored questions; and per question what each arm found and missed.

Exit Meaning
0 The run finished (and met min_recall, if the file sets one).
1 The graph arm's recall@k is below min_recall.
2 The run could not execute or has no score: the endpoint was unreachable, it has no search tool, any graph-arm call failed, a file was unusable, or the set's bundle is not the instance's.
3 With --agents: the agent arms stopped at the spend cap. The report holds what completed. With --agents, exit 2 also means the run refused before any model call, or the model endpoint refused a request no retry can fix (a 4xx other than 429).

A failed baseline call counts as a baseline miss and is listed; a failed graph call leaves the run without a score.

The score and the context gate

The score is the graph arm's recall@k. The context gate of an automation with min_context_eval_score reads the newest run of one bundle under <data root>/eval/context/<bundle>/: the gate's context_eval_bundle, or the instance's only bundle. Only that newest run counts. The context_eval check fails, naming the reason, when that run:

  • cannot be read, or is not an archi-context-eval-report/1 report of that bundle;
  • did not execute cleanly (status execution_failed, or any graph-arm call failed);
  • ran a graph arm the question file overrode;
  • lacks its question-file hash, or its scored-question count does not match its rows;
  • finished more than max_age_days ago (a gate key: above 0, at most 3650; default 14 days), or more than five minutes in the future;
  • used another k than context_eval_k, or scored fewer questions than context_eval_min_questions (both optional gate keys, unset by default);
  • or scores below min_context_eval_score.

A run written elsewhere with --out, or against --mcp-url, is not read by any gate.

The instance-health automation does not read context evals. It reads only the smoke reports (archi-eval-report/1) and never looks under <data root>/eval/context/ or in hidden directories, so a broken context-eval file cannot break its eval signal.

The raw-document baseline: --raw-corpus and --agents

The two arms above search the same server. The raw-document baseline asks a different question: does the graph help an agent find the evidence, compared with the same agent reading the files the graph was built from? It adds two agent arms to a context run. Both use one model, one prompt and one set of caps; they differ only in where the knowledge is.

Arm What the agent has
agent-bash One tool, bash, over the raw corpus. Each command runs in a bubblewrap sandbox: no network, the corpus mounted read-only at /corpus, a fresh in-memory HOME, an empty environment, and rg, jq and python3 on PATH when the host has them. Limits: 120 s of wall time and 64 KiB of output per command (a command over either is stopped), and per process 256 processes, 4 GiB of address space, 256 MiB per file written, and CPU time equal to the wall limit. Where the user's systemd manager runs, each command also runs in its own systemd-run --user --scope, which caps the whole command, in-memory files included, at 4 GiB of memory, no swap, and 256 tasks. Where it does not, the run prints a note and the report records limit_scope: process: the per-process limits then hold, but several processes of one command, or its in-memory files, can together use more. If the scope stops starting during a run, the run aborts (exit 2) rather than show the model systemd's error.
agent-graph The instance's MCP tools.

The prompt is the same text for both, except the one paragraph that says where the knowledge is. The report holds both prompts.

bubblewrap 0.6.3 cannot size its in-memory mounts, so the per-file size limit is what bounds a write to /tmp or HOME. The process limit counts processes in bwrap's own user namespace (Linux 5.14 and later); on an older kernel, which counts every process of the user, the limit becomes the user's current count plus 256. Starting the arm runs true and a small pipeline through the real sandbox first, and refuses (exit 2) if either fails.

These arms call a model, which may be a paid one. Every call is written to a spend ledger, and the run stops at a cap you set.

Build the corpus

archi eval --raw-corpus --bundle cms-comp-ops

This reads the instance's source_registry.yaml and takes each enabled source whose connector cache an archi.snapshot group reads. Each cache is packed with the snapshot builder, which checks every file with the source's own reader, removes email addresses and drops the fields the reader does not read. The archives are then unpacked, one file per record, to <data root>/eval/raw-corpus/<bundle>/<lock sha>/, where <lock sha> is the start of the snapshot lock's SHA-256:

File What it holds
records/<group>/... One file per record. Only this directory is mounted into the sandbox.
MANIFEST.txt <path> and <sha256> of every record file. The corpus digest is the SHA-256 of this file.
keys.json Per source, the names a node id may give (natural key, node id) mapped to a file, and each file's natural key.
corpus.json, README.md The digest, the published generation, the coverage line, the sources, and every source left out with the reason.

What goes in.

  • A git-code checkout goes in as its tracked files at HEAD (git ls-files), under records/git-repo/<repo>/, one per enabled git-code repository. It does not go through the snapshot, because no snapshot group checks a source tree. Email addresses are removed here, as the snapshot does, and binary files and files over 1 MiB are left out and counted. The HEAD of each repository is recorded.
  • TWiki keeps only the pages the instance's TWiki reader reads, with the instance's own physics_filter, seed_topics, skip_patterns and max_files. A cms-physics corpus therefore holds the physics pages the graph read, not the whole dump. page_index_path changes no page, so it is not needed.

What stays out. A source with no cache for the snapshot to check is left out and named:

  • live fetches: indico_live, cds (harvested from CDS at ingest, with no copy on disk), MONIT;
  • analysis_notes: a LaTeX mirror that no snapshot group checks yet;
  • derived sources.

A cache the snapshot refuses refuses the whole corpus, and nothing is written. Derived files and okg state are never read. The coverage line says all of this in one sentence, for example cms-physics: cmssw_releases, twiki_eos (physics filter); analysis_notes not included: ...; cds not included: ....

ops-record is left out of both arms. Its records exist only in the graph, written through okg admission; there is no cache. An export through the MCP tools could not be shown to be complete, so the corpus does not hold it, and its gold records count as unavailable in both agent arms: they leave the denominator and are listed. The agent-graph arm can still read ops records through its tools, but they earn it nothing.

Corpus and generation. The build reads the published generation through MCP inspect(graph) and records it beside the digest. A run reports both, and warns when the generation it evaluated differs: the arms may then not see the same records. A corpus whose files no longer match its manifest, or that holds a symbolic link under records/, is refused.

Run the agent arms

export ARCHI_EVAL_MODEL_KEY_FILE=/path/to/file-holding-the-key
archi eval --context --questions /path/to/operator-questions.yaml \
  --agents --model <model> --model-url https://api.openai.com/v1 --allow-remote-model \
  --reasoning-effort medium --model-price IN/OUT/CACHED --tries 3 --cap 10
Option Meaning
--agents [ARMS] Run the agent arms too: both by default, or agent-bash or agent-graph alone.
--tries N Tries per question and arm (default 1).
--corpus DIR The corpus. Default: the newest under <data root>/eval/raw-corpus/<bundle>/.
--model, --model-url The model, at any OpenAI-compatible endpoint. A remote one needs --allow-remote-model. temperature and seed are never sent to a remote endpoint.
--model-key-env VAR The variable that holds the path of a file with the API key (default ARCHI_EVAL_MODEL_KEY_FILE). The key is never logged, never written to the report or ledger, and never enters the sandbox.
--model-price IN/OUT[/CACHED] Dollars per million input, output and cached-input tokens. Required: the ledger needs it. A price below $0.01 input or $0.04 output per million is refused as a likely typo unless --allow-low-price is given (for a local model).
--reasoning-effort E Sent with each agent call.
--model-api auto\|chat\|responses The API the agent calls use. auto (the default) uses OpenAI's Responses API (/responses) for api.openai.com and /chat/completions for anything else, such as a local Ollama. Some OpenAI models take function tools with a reasoning effort only on /responses. Nothing is stored at OpenAI (store: false): each request sends the whole conversation back, with the encrypted reasoning of earlier turns. The ledger counts tokens the same way for both APIs, cached and reasoning tokens included, so --cap holds for both.
--max-turns, --max-tool-calls, --try-seconds Caps per try: 30 model turns, 200 tool calls, 900 s by default. A call is not started with under 60 s of the try left.
--max-output-tokens N max_completion_tokens per agent call (max_output_tokens on the Responses API; default 16000); also the spend guard's bound.
--cap DOLLARS The spend cap for the invocation, judge included and every question set together. Required: there is no default.
--judge Grade answers with a judge model. Off by default.
--judge-model, --judge-url, --judge-reasoning-effort, --judge-key-env, --judge-price, --judge-max-output-tokens The judge: any OpenAI-compatible endpoint (default https://api.openai.com/v1, reasoning high, key file path in ARCHI_EVAL_JUDGE_KEY_FILE, at most 16000 output tokens per call). The judge sends no tools and always uses /chat/completions; --model-api does not apply to it.
--judge-passes 1\|2 Judge each answer once or twice; the score is the mean.

Before any model call, the run refuses (exit 2) and names the reason when:

  • there is no cap or no price, or the price is implausibly small;
  • the corpus's files no longer match its manifest, it holds a symbolic link, or it belongs to another bundle;
  • agent-bash was asked for and bwrap is not installed, or the sandbox cannot start;
  • any gold id does not resolve (see below).

Nothing is installed for you.

Model failures.

  • A 429 or 5xx reply is retried with backoff (Retry-After when given, else 4, 8 and 16 s), at most three times.
  • A context-length error, or a reply that stops at max_output_tokens with no answer, ends that try as an error.
  • Any other 4xx (a bad key, a bad request) aborts the run, exit 2. The report keeps what completed.

Error tries are listed per arm with their reason, counted, and left out of evidence recall and MRR.

How gold ids map to files

Each gold id is read with the MCP inspect tool, which returns its subtype, attributes and source. The source and the node id (or, for a documentation page, its URL) are looked up in keys.json. The source is matched as okg writes provenance: the <deployment>. prefix is dropped and - reads as _, so cms-physics.twiki-eos finds twiki_eos. A question can name a record directly instead:

questions:
  - id: transfer-errors
    question: Why do transfers to the site fail?
    gold: [jira:CMSTRANSF-123, chunk:9f2a1c]
    answer: The storage certificate expired.     # optional answer key, for --judge
    gold_sources:                                # optional; overrides inspect for these ids
      chunk:9f2a1c: {path: jira/CMSTRANSF-123.json}
    atoms:                                       # optional: the facts an answer needs
      - {id: a1, answer_source: ticket, gold: [jira:CMSTRANSF-123]}
      - {id: a2, answer_source: live_rucio}

A gold record is unavailable, and so leaves the denominator in both arms and is listed, when:

  • its source is left out of the corpus (ops-record, a live source);
  • its record has no field value or line distinctive enough to recognise;
  • every value or line of its record long enough to recognise also appears in another corpus record;
  • the only atoms that carry it are answered by a live system alone (answer_source of live_rucio, live_dbs or monitoring). An atom like that is listed in the report, separately. A mixed atom (ticket+live_rucio, doc or ticket) counts through its file source.

A gold id that inspect cannot find, or whose record is not in the corpus, makes the run refuse to score, naming the id and the reason. It is never counted as a miss.

Question sets that name evidence in prose. A benchmark such as CompOps-42 names its evidence in a sources: list and in verification.evidence, not as node ids. Draft the mapping with:

python -m archi.evaluation.draft_gold_sources --questions <dir of golden YAML> --out <private file> \
    [--repos <dir of git checkouts>]

It recognises these kinds of reference:

  • Jira keys become jira;
  • repos/<repo>[ @<sha>] <path> becomes the git-code file <repo>/<path>;
  • a repository document named loosely (<repo>/<file>.md, <org>/<repo> <path>.md, <repo> Documentation <path>.md, <repo> Documentation: <a_b_c>.md, or documentation_page:<repo>:<a_b_c>.md; also .rst, .txt and .markdown) becomes a git-code file. Such a name may leave out folders, spell the repository differently from its checkout, or flatten the path (_ or - for / and spaces). With --repos, a directory holding one git checkout per repository, each is resolved to the one file it names. One that matches no file or several, and every one when --repos is not given, goes to unresolved and gives no reference;
  • documentation URLs become docsite;
  • CMS site names become cric.

It writes per question a draft gold, gold_sources and atoms, with a confidence note on each reference and an unresolved list for a person to review. The draft is private to the set: keep it beside the set, never in this repository. The command refuses an --out inside it. A person who knows the answer key reviews the draft before a run uses it.

To check that gold ids keep naming the same records from one published generation to the next, sample 20 of them at two generations:

python -m archi.evaluation.gold_check --questions FILE \
  --generation-a <older generation> --generation-b <newer generation> [--corpus DIR]

It exits 0 when every sampled id is visible at both with the same subtype, source and (with --corpus) record, and 1 otherwise. It calls only MCP.

How the agent arms are scored

The same scorer reads both arms' transcripts: every tool response the model saw, including the visible part of a response that was cut and the output of a bash command that exited non-zero. What the agent typed (tool inputs) and its final answer never count.

  • A gold record is read when the responses show two of its field values or lines (or its only one). A value or line shows when a run of six of its words appears, or, for a value of four or five words, the whole value. A value under four words never counts, and neither does a title field (summary, title, subject, short_description, topic, headline, label, name, displayName): like a file name, a search row shows it beside every hit. A record whose only long text is a title is unavailable, and the report counts unavailable gold records by reason. Words are compared lower-cased, ignoring punctuation and JSON escapes, so a cat of the file and an MCP excerpt of the same text both count. A search row with one excerpt, or one line a grep matched, therefore only lists a record that has more to read.
  • Text another corpus record also holds never counts: before the run, one pass over the corpus drops every gold fingerprint found in a second file (a from __future__ line, a TWiki %META line, a licence header). A gold record left with nothing is unavailable, and the report counts what was dropped per record. Text in graph nodes that have no corpus file (a source left out of the corpus) is not checked.
  • A record named only by its path, natural key or node id is listed, not read. The report counts listed records per try, and they earn no credit. A natural key shorter than six characters does not even list a record.
  • Evidence recall, per try: the share of the question's available gold records read. The arms take turns going first, and recall and MRR compare them only on the (question, try) pairs every arm finished without an error: a spend stop or an error try can leave one arm with a try the other lacks, and that try is counted under tries_unpaired, not scored. The answer score is paired the same way. With one arm, an error try is left out of its averages too (it is listed under failures), not scored as recall 0.
  • MRR: 1 / the rank of the first gold record read among the distinct records the agent met, in order. Other records count as met when their path or node id appears.
  • Answer score: with --judge, the judge's mean score (0, 0.5 or 1) over the answers to questions that have an answer. Without answer keys the column says no answer keys; with keys but no --judge, judge off. Never 0 for a missing key.

The report keeps graph and baseline as they are and adds the agent arms under agent_arms, with one table of all four side by side: evidence recall (recall@k for the search arms), MRR, listed-not-read, answer score, cost per try, tool calls per try, and failures (errors, tries that hit a cap). It also records the corpus digest, generation and coverage, the model, the caps, both prompts, the resolved gold map, the live-only atoms and the spend. The context gate still reads only the graph arm's recall@k.

Spend

Every model call, agent or judge, answered or not, adds a row to <data root>/eval/context/<bundle>/<stamp>/ledger.jsonl. A row holds the arm, the question and try, the model, the outcome, the input, cached, output and reasoning tokens, and the cost. Some calls are charged at their bound, not at their tokens:

  • a call that failed after it was sent (it may still be billed);
  • a reply that carried no token usage, which also prints a warning.

A call that never reached the endpoint is not charged. During the run the ledger is written in a hidden directory beside the runs and moved into the run's directory with the reports. With --out it is written there directly. One invocation keeps one cap across all its question sets, with one ledger file per run directory.

Before each call the run bounds its cost: the request's size in bytes / 3 for input tokens, plus --max-output-tokens. Before the first call it prints that bound for a first call and for a call with 128k tokens of context, so a wrong price shows before money is spent. When the bound would take the spend past --cap, the call is not made. The run stops cleanly, the report says what completed (a try cut short is listed, not scored), and the command exits 3.

Testing the sandbox

The sandbox tests in python/tests/evaluation/test_raw_sandbox.py run real bwrap. They are skipped, with the reason, on a host without it, which includes CI. Set ARCHI_REQUIRE_BWRAP=1 to make them fail instead, on a host that must prove the sandbox.
