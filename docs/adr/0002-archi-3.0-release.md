# ADR 0002 — Archi 3.0: automating operations on a solid context layer

**Status:** proposed (2026-10-24), from the Archi discussion at the CERN
Knowledge Bases & Agents workshop (indico.cern.ch/event/1716863, 22/10/2026).
**Amends:** ADR 0001. Its architecture (OKG substrate → Archi distribution →
instances) and its non-goals stand. Its branch rules (§6.3, §14, invariant 2)
and its "one bundle in the first draft" rule (W6) are replaced here. Its W8
(automations) moves into 3.0 as the operations layer (§7).
**Tracking:** GitHub milestones `3.0 · M0` … `3.0 · M7` on
`archi-physics/archi`; one PACT per work package under `pact/changes/r3-*`.
`pact/plan/archi-3.0.yaml` maps each PACT task to its issue.

---

## 1. What Archi 3.0 is

**Archi automates operations for scientific computing:** experiment
computing operations, analysis user support, data quality, and cluster
management. Agents watch the system, triage what comes in, propose actions,
and once a policy or a person approves, a mediator carries the action out.
Every step is grounded in, and recorded back into, the facility's own
knowledge.

Automation is only as good as what the agent knows. So 3.0 is two layers
on top of OKG:

1. **The context layer.** It holds what the facility knows: documentation,
   tickets, catalogs, monitoring, code, and the record of past operations.
   It has to be **solid**: current, complete for the questions the
   automations depend on, linked across sources, cited on every read, and
   measured (§6). Packs and bundles (§3) are how a facility gets one.
2. **The operations layer.** Automations close the loop *signal → context →
   proposal → decision → action → outcome*. Actions run under explicit
   autonomy levels, up to L2 in 3.0, and OKG's review machinery (§7). Outcomes are written back
   into the context layer, so the next triage can see what happened last time.

The operating principle from the workshop: **algorithmic first, agents for
judgment.** Deterministic checks (invariants, freshness, lint, thresholds,
evals) decide everything they can. Agents handle what needs reading and
judgment. Agents also monitor and help develop the Archi instances
themselves (§7.5).

Every component stays replaceable. Archi is the glue that holds them
together, and its defaults work out of the box:

| Layer | 3.0 default | How it is replaced |
|---|---|---|
| Context substrate | OKG (AKMON) | the MCP tool surface (`search`, `expand`, `inspect`, `filter`, `map`, `aggregate`) |
| Ingestion | archi connectors | any pip package exposing `SourceAdapter`s through the `archi.packs` entry point (§4.4) |
| Tools / MCPs | the instance's OKG MCP server plus archi live tools | any MCP server declared in the instance (§4.5) |
| Automation runtime | OKG deployment workflows (DBOS) plus escalations and Nomos | an external runner using the proposal API (upstream ask, §9) |
| Agent / chat | Open WebUI, built in | anything that speaks MCP: Claude Code, codex, openclaw, custom harnesses |
| LLM | whatever the agent is configured with (CERN AIGW and local ollama documented) | agent-side configuration |
| Observability | OKG telemetry and `llm_calls` tables | Langfuse is **deferred** past 3.0 |

**Who it is for, in order:** (1) operations teams: CMS comp-ops, CRAB
support, WisDQM, and cluster managers like SubMIT. The release bar is
measured against these teams (§10). (2) A CERN team operator who only wants
the context layer and an agent over it in an afternoon. They get the same
bundles with no automations selected.

## 2. Decisions

- **D1. The release home is `archi-physics/archi`.** archi-okg `main`
  becomes the v3 line there. The current `archi_v3` tip is kept as the tag
  `archi_v3-pre-merge` and then replaced. At cutover the v3 line becomes
  `main`, and v2 is kept as the `v2` branch with its `v2.x` tags.
  archi-okg is archived and its README points here.
- **D2. The PyPI distribution is `archi-kb`.** The import name stays
  `archi`. CI publishes with PyPI trusted publishing. Release version: `3.0.0`.
- **D3. Bundles compose.** A bundle is a named selection of **packs** (§3).
  There are three kinds of pack: *context* packs (sources), *tool* packs
  (live tools) and *automation* packs (§7.2). Several bundles can be
  installed into one instance.
- **D4. The 3.0 bundles are:** `cern-team`, `cms-comp-ops`, `cms-physics`
  and `cluster-manager` (§5). There is no `cms-kb` bundle: the cms-kb
  deployment is the validation instance of `cms-physics`.
- **D5. Open WebUI is one built-in client, not the product.** The supported
  surface is the instance's MCP endpoint. `archi connect <client>` writes the
  client config for Open WebUI, Claude Code, codex, openclaw, and generic
  MCP over HTTP.
- **D6. Setup is one command.** `archi init` + `archi up` takes an empty
  machine to an answered question (§8). The current 1,016-line quickstart
  becomes reference material.
- **D7. The archi CLI is thin.** It renders a composed profile and passes
  it to `okg install` / `okg chat-instance`. It never reimplements an okg
  step. Every place where it covers for an okg gap is filed upstream
  (§9), and is removed once okg ships the fix. This keeps ADR 0001
  invariant 4.
- **D8. Langfuse is deferred.** It is not in the 3.0 stack.
- **D9. Planning is done with PACTs, GitHub milestones and issues.** Each
  work package is one PACT. Each PACT task is one issue, labelled
  `pact:<id>`. Each PACT gets one epic issue that lists its tasks. Milestones
  follow §10.
- **D10. Operations automation is the purpose of 3.0, not a follow-up.**
  3.0 ships the operations layer and one reference automation,
  `ticket-triage`, running in shadow on its validation instances (§7.4).
  Promoting it to live is a 3.1 goal. The release does not wait for it.
  ADR 0001 W8 is folded in here.
- **D11. Agents propose, mediators act.** No agent holds an execution
  credential. An action is a typed *action class* carried out by a mediator
  (a live tool or a workflow step) only after its autonomy policy allows it.
  ADR 0001 D3 and invariant 5 still apply: decisions are recorded in OKG's
  ledgers, and execution stays in the automation.
- **D12. An automation depends on measured context.** Each automation
  declares the context it needs (sources, freshness, eval set). It runs
  live only while that context passes its gates (§6.3). Otherwise it drops
  to shadow mode and says why.
- **D13. 3.0 stops at L2.** No automation acts without an approved
  escalation. L3 is reserved, and the 3.0 runtime refuses to configure it
  (§7.3).

## 3. Packs and bundles

### 3.1 Pack

A pack is the smallest installable capability. A context pack covers one
source family; tool packs and automation packs are described in §7.2. A
pack lives at `bundles/packs/<name>/pack.yaml`:

```yaml
name: indico
kind: context                # context | tool | automation
version: 0.1.0
description: Indico events and contributions (public or token-authenticated).
requires:
  modules: [document_starter, extraction]   # okg ontology modules
  packs: []                                  # other packs this one needs
schemas: schemas/            # LinkML slices; merged by path (§3.3)
sources: sources/            # source-registry templates, one file per source
init_questions: questions.yaml
invariants: invariants.yaml  # owned by this pack; leave with it
freshness:                   # §6.1; checked by archi doctor
  indico.events: {max_staleness: 24h}
playbooks: skills/
skill_triggers: skills/skill-triggers.yaml
search_subtypes: [indico_event, indico_contribution, document_chunk]
live_tools: []               # archi.tools.* entries for the MCP server
prompt_fragment: prompt.md   # appended to the chat system prompt
credentials: [INDICO_TOKEN]  # env-var names only, never values
needs_credentials: false     # true ⇒ cannot be a bundle's only default pack
```

### 3.2 Bundle

A bundle is a named, versioned selection of packs, plus a chat preset and
an eval set. It lives at `bundles/<name>/bundle.yaml`:

```yaml
name: cms-comp-ops
version: 0.1.0
extends: [cern-team]          # bundles, resolved transitively
packs:
  default: [cms-catalogs, cmssst, cmssw-releases, ops-record]
  optional: [monit-live, hypernews, jira, ticket-triage]
chat:
  site_name: CMS Computing Operations
  suggestions: [...]
eval: eval/smoke.jsonl        # run by `archi eval` and by CI
okg: ">=0.2.0,<0.3"           # supported AKMON range
```

### 3.3 Composition rules

`archi init <instance> --bundle A [--bundle B ...] [--with p] [--without p]`
resolves:

```
packs = companions(closure(requires, ∪ default(extends*(A, B, ...))) ∪ with) − without
```

and renders the result into one okg profile.

*Amended 2026-10-31 (PACT `r3-bundle-companions`, decision d716):* a bundle
may name **companion packs**, `packs.companions: {<pack>: [<companion>, ...]}`.
`companions(S)` adds to `S`, for each pack in `S`, its companions and the packs
they require, unless the companion or its trigger is given to `--without`.
Removing a companion is the opt-out and is not refused, even before its
trigger is selected (`archi init --without`, `archi add --without`).
cms-comp-ops uses it
so that selecting `git-code` also brings `code-text` (the files' text), while
an install without `git-code` is unchanged. Companions merge over `extends`,
parents first, and across several `--bundle`s as a union (a later bundle
cannot cancel an earlier one's companion). A companion the catalog does not
hold fails bundle validation, and `archi init` names that problem.

Rules:

| Part | Rule |
|---|---|
| modules | set union |
| schemas | union by relative path. Two packs shipping the same path must be byte-identical, otherwise `archi init` stops with both digests |
| sources | ids are `<pack>.<source>`. A pack selected twice installs once |
| init questions | union. The same id must have an identical definition. Answers become `--<pack>-<id>` flags |
| invariants, freshness SLOs | union. Each belongs to its pack, so dropping a pack drops them. This fixes the cern-team "core pages floor" problem |
| search profile `content` | subtype union |
| playbooks / triggers | union. The same filename must be identical |
| action classes | union by id. The same id must be identical. The autonomy level is set per instance, never by the bundle (§7.3) |
| chat system prompt | base prompt, then each pack's `prompt_fragment` in resolution order |
| chat scalars (site name, default model) | taken from the last `--bundle` given. Earlier conflicting values are reported |
| `okg` range | intersection. If it is empty, init stops |

Two properties must always hold. **A bundle with nothing configured
publishes:** each bundle needs at least one default context pack with
`needs_credentials: false`, or a required init question. **A pack that is
not selected leaves no trace in the rendered profile.** This removes today's
"rename `.yaml.example` to opt in" step and the "installed but inactive
source blocks the publish" trap.

The rendered profile and an `archi.lock` (bundle and pack versions plus
content digests) are committed into the instance repo. Instances still
diverge freely after install (ADR 0001 §2.1). `archi add <pack>` adds a pack
to an existing instance, including the registry edit and the ownership
re-claim that the quickstart currently documents as manual steps.
`archi diff` shows how an instance has drifted from its lock.

### 3.4 Packaging and discovery

Bundles and packs ship inside the `archi-kb` wheel as real files, with no
symlinks. `archi bundles list|show` finds them through the `archi.bundles`
and `archi.packs` entry points. Third-party packages, such as the ingestion
WG's, register packs the same way. `OKG_PROFILES_DIR` is set by the CLI and
is never typed by a user.

## 4. Swap points

4.1 **Agent/chat:** `archi connect open-webui|claude-code|codex|openclaw|mcp`.
Each is a tested recipe that writes client config pointing at the
instance's MCP endpoint, with its token.
4.2 **LLM:** never stored by archi. The docs cover CERN AIGW and local ollama.
4.3 **Context substrate:** OKG only in 3.0. The MCP tool surface is the
contract that other KBs would have to meet.
4.4 **Connectors from elsewhere:** a pack published by another package
through the `archi.packs` entry point. The connector contract is the okg
`SourceAdapter` plus the pack manifest.
4.5 **External MCP servers:** declared in the instance's `archi.yaml`
`mcp_servers:` block. `archi connect` registers them next to the instance's
own server. Archi runs none of them.

## 6. The context layer: what "solid" means

Automations act on what the context layer says. "Solid" therefore has to
be measurable, checked mechanically, and gated on. It is never just asserted.

### 6.1 Properties, each with a mechanism

| Property | Mechanism | Where it is checked |
|---|---|---|
| **Current** | each source declares `max_staleness`; okg's watermarks give its actual age | `archi doctor`; automations' context gate |
| **Complete** | each pack owns coverage invariants over what it should emit; completeness gates block a partial publish | okg publish gate; `archi doctor` |
| **Linked** | enrichment links identifiers (sites, datasets, runs, releases, tickets, analysis ids) across sources; each pack declares its link coverage target | link-coverage invariant per pack |
| **Cited** | every read is generation-pinned, and every answer or proposal cites record ids | MCP surface (okg); proposal schema (§7.2) requires citations |
| **Measured** | each bundle ships a *context eval*: operator questions with gold evidence. It is scored on retrieval (was the right evidence found) separately from answer quality, with a raw-document baseline arm | `archi eval --context`; CI per bundle |
| **Clean** | redaction (emails, personal data) and anonymisation at ingest; no credentials in the graph | connector tests; ingest-time checks |

### 6.2 Operational memory

The `ops-record` pack adds a schema slice and an admission path for the
record of operations:

- **incident:** what broke, where, when
- **proposal:** what an automation suggested, and on which evidence
- **decision:** who or what approved or rejected it, and when
- **action:** what the mediator ran, and what it returned
- **outcome:** whether it worked, checked later

Automations write these records through admission like any other producer.
Humans' ticket resolutions arrive through the ticket connectors. Past
resolutions then become context ("this transfer error last time was fixed
by…"), and the operations record also serves as the eval set for the next
automation.

### 6.3 Context gates

An automation declares its required context: sources, maximum staleness,
a minimum context-eval score on its question set, and the invariants that
must hold. Before each run, the runtime checks the gate against the current
generation. A failing gate downgrades the run to **shadow** (propose and
record, never act). The proposal carries the failing check, so the
operator sees *why* the automation would not act.

## 7. The operations layer

### 7.1 The loop

```
signal ──► context read ──► proposal ──► decision ──► action ──► outcome
(schedule,   (pinned          (agent,      (autonomy    (mediator,   (checked,
 ticket,      generation,      cited,       policy,      typed        written to
 alert)       context gate)    typed)       Nomos,       action       ops-record)
                                            escalation)  class)
```

It runs as an OKG deployment workflow: DBOS-scheduled, `llm_call` with a
`cost_budget`, and `request_escalation` for decisions that need a person.
Durable state lives in DBOS, never in a local file (the ADR 0001 Appendix B
lesson).

### 7.2 Automation packs

An automation pack declares:

- **trigger:** a schedule, a new ticket in a queue, or a watched signal
  (a monitoring threshold, a site status change)
- **context gate** (§6.3)
- **playbook:** the instructions the agent follows
- **action classes:** each with a typed payload schema, its mediator (a live
  tool or a workflow step), whether it is reversible, a blast-radius note,
  and the highest autonomy level it is *allowed* to have (at most L2 in 3.0)
- **proposal schema:** summary, cited evidence ids, proposed action class
  and payload, confidence, and rollback
- **budget:** cost per run and per day; runs per hour

Tool packs (`monit-live`, `slurm`, …) ship the live tools that act as
mediators. An automation never calls an external system any other way.

### 7.3 Autonomy levels

| Level | Meaning | 3.0 |
|---|---|---|
| **L0 observe** | writes findings to ops-record and dashboards only | yes |
| **L1 draft** | drafts a reply or a ticket for a person to send | yes |
| **L2 propose** | proposes an action; it runs only after an escalation is approved; timed-out proposals never run | yes |
| **L3 act within envelope** | runs a reversible action class without review, within rate and budget limits | **no.** Reserved; the runtime refuses an L3 setting. Revisit once L2 automations have a live track record |

Three rules:

- The instance sets each automation's level in its own `archi.yaml`. A
  bundle only sets an upper bound.
- Every automation starts in **shadow** at its configured level: it proposes
  and records, and its proposals are scored against what humans actually
  did.
- Promotion to live needs recorded shadow results and an operator's
  approval, recorded as a PACT decision on the instance. `archi ops halt`
  (wrapping okg pause/drain until the upstream kill switch lands) stops
  every automation on an instance.

### 7.4 The reference automation: ticket triage

**`ticket-triage`** is the one automation 3.0 focuses on. It runs in
cluster-manager at SubMIT and on the cms-comp-ops queue.

- It reads new and updated tickets from Redmine, JIRA or ServiceNow.
- It finds related past tickets, docs and precedents.
- It drafts a cited reply (L1) or proposes a status or assignment change
  (L2).

It unifies ADR 0001 W8's queue bots. The ticket system's status reflects
the escalation ledger and is no longer the source of truth.

**The 3.0 bar:** it runs in shadow on both instances, and a report covering
at least four weeks of shadow results is published with the release. The
report covers agreement with operators, time-to-first-response and
false-proposal rate. Promoting it to live is the 3.1 goal. The v2 queue
bots keep serving until that promotion, on a tagged `v2.x` under the
ADR 0001 §14 cutover rules.

**After 3.0, on the same runtime:** `compops-watch` (cmssst, WMStats and
MONIT signals; triage notes; drafted tickets and Rucio rule proposals),
`node-health-watch` for cluster-manager, and CRAB user support.

### 7.5 Agents operating Archi itself

A built-in L0/L1 automation watches each instance: doctor results,
freshness against SLOs, context-eval regressions, failed ingests, and
automation error rates. It opens issues or draft PRs against the instance
repo. This is the workshop's "use agents to monitor & develop these",
applied to the system itself.

## 8. The setup path

```bash
uv tool install archi-kb
archi init myteam --bundle cern-team --with indico,git-code   # instance repo, .env, lock
archi up                  # compose: akmon-postgres, chat postgres, Open WebUI, MCP server, worker
archi doctor              # okg lint + doctor + freshness + archi's footgun checks, --json for agents
archi connect claude-code # or open-webui / codex / openclaw / mcp
archi ops status          # automations, levels, shadow scores (when automation packs are selected)
```

- `init` creates the instance directory as a git repo and generates every
  secret into `.env`. It makes every data path absolute and puts the data
  root outside the deployment directory, because `okg install --force`
  deletes everything inside it.
- `up` starts one compose project (podman or docker) on one network. That
  removes the container-gateway address, the separate long-running MCP
  process, and the `--ready-timeout` tuning. It starts the runtime worker
  only when an automation pack is selected.
- Every footgun in today's quickstart is listed in the `r3-golden-path`
  PACT as either **absorbed** (archi handles it) or **filed** (okg issue
  linked).
- Acceptance: a nightly CI job goes from an empty VM to a cited answer
  with `cern-team` defaults in at most 15 minutes, using at most 5 user
  commands.

## 9. Upstream asks (AKMON)

Filed against AKMON and tracked on archi with the `upstream-ask` label:

1. AKMON wheels on PyPI, and a proven non-editable install (no
   `pip install -e` of a clone).
2. Profile discovery through entry points, so `OKG_PROFILES_DIR` is not needed.
3. Profile composition and optional sources, so archi's renderer can be
   deleted.
4. Role passwords set during `okg migrate` on password-authenticated servers.
5. `okg chat-instance up` also starts the instance's MCP server.
6. Publishing from a deployment directory that is not a git repo, with
   provenance recorded as standalone.
7. **For the operations layer** (ADR 0001 §7 asks 3–4, now on the 3.0
   critical path):
   - expiry on admission envelopes
   - approve-with-edits
   - a mounted, authenticated proposal API
   - per-actor cost attribution on `llm_calls` / `mcp_call_log`
   - a first-class kill switch
   - a retraction-size guard (mitdbg/akmon#19)

   Until these land, automations run co-located as deployment workflows,
   edits are handled as reject-and-resubmit, and `archi ops halt` wraps
   pause/drain.
